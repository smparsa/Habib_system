# Habib_system — نسخه جنگو (Django)

این پروژه، نسخهٔ استاتیک HTML/CSS/JS شما (index.html, dashboard.html, profile.html) را در قالب یک پروژهٔ استاندارد **Django** بازسازی کرده است:

- صفحات HTML → به `templates` جنگو تبدیل شدند و از طریق ویوها (views) سرو می‌شوند.
- فایل‌های css/js/assets → به پوشهٔ `static` منتقل و به تگ `{% static %}` جنگو مجهز شدند.
- مسیرها (URLs):
  - `/` → صفحهٔ ورود (index)
  - `/dashboard/` → داشبورد
  - `/profile/` → پروفایل
  - `/admin/` → پنل ادمین جنگو (پیش‌فرض)

## ساختار پروژه

```
habib_system/
├── manage.py
├── requirements.txt
├── habib_system/       ← تنظیمات اصلی پروژه (settings.py, urls.py)
└── core/                   ← اپ اصلی
    ├── views.py            ← ویوهای سه صفحه
    ├── urls.py             ← مسیرهای اپ core
    ├── templates/core/     ← فایل‌های html (index, dashboard, profile)
    └── static/core/        ← css, js, assets (logo, تصاویر)
```

## نصب و اجرا

1. (اختیاری ولی توصیه‌شده) ساخت محیط مجازی:
   ```bash
   python3 -m venv venv
   source venv/bin/activate      # ویندوز: venv\Scripts\activate
   ```

2. نصب وابستگی‌ها:
   ```bash
   pip install -r requirements.txt
   ```

3. اجرای مایگریشن‌های اولیهٔ جنگو (برای auth/admin/session):
   ```bash
   python manage.py migrate
   ```

4. اجرای سرور توسعه:
   ```bash
   python manage.py runserver
   ```

5. باز کردن در مرورگر:
   - http://127.0.0.1:8000/  → صفحه ورود
   - http://127.0.0.1:8000/dashboard/ → داشبورد
   - http://127.0.0.1:8000/profile/ → پروفایل

## پایگاه‌داده: MySQL

پروژه به‌جای SQLite حالا به **MySQL** وصل می‌شود (نام دیتابیس پیش‌فرض: `habib_db`).

برای اتصال از **PyMySQL** استفاده شده (نه `mysqlclient`) چون خالص پایتون است و روی ویندوز نیازی به Build Tools/کامپایلر ندارد (شبیه مشکلی که با Pillow پیش آمد).

### نسخهٔ Django و سازگاری با MySQL
این پروژه روی **Django 5.1.4** پین شده (نه آخرین نسخه). دلیل: نسخه‌های جدیدتر Django (6.x) حداقل به **MySQL 8.4** نیاز دارند، درحالی‌که خیلی از سرورهای رایج هنوز MySQL 8.0.x دارند. Django 5.1 با MySQL 8.0.11 به بالا کاملاً سازگار است، پس نیازی به آپدیت سرور دیتابیس‌تان نیست.

اگر سرور MySQL شما 8.4+ است و می‌خواهید از آخرین Django استفاده کنید، کافی است در `requirements.txt` نسخه را به `Django` (بدون پین نسخه) یا `Django==6.1` تغییر دهید و دوباره `pip install -r requirements.txt` بزنید.

### ۱) ساخت دیتابیس و کاربر در MySQL
پروژه به‌صورت پیش‌فرض به کاربر اختصاصی `habib_user` (نه root) وصل می‌شود. این دستورات را یک‌بار در MySQL Workbench یا خط فرمان mysql (با کاربر root یا هر کاربری که دسترسی ساخت دیتابیس/کاربر دارد) اجرا کنید:
```sql
CREATE DATABASE habib_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'habib_user'@'localhost' IDENTIFIED BY 'Habib@12345';
GRANT ALL PRIVILEGES ON habib_db.* TO 'habib_user'@'localhost';
FLUSH PRIVILEGES;
```
همین. با همین یک بار اجرا، تنظیمات پیش‌فرض پروژه (در `settings.py`) بدون نیاز به هیچ متغیر محیطی کار می‌کند.

### ۱.۱) اجرای تست‌ها (`manage.py test`)
کاربر `habib_user` فقط روی `habib_db` دسترسی دارد و نمی‌تواند دیتابیسِ تست (`test_habib_db`) بسازد. برای اینکه تست‌ها بدون هیچ دسترسی اضافه‌ای اجرا شوند:

```bash
python manage.py test --settings=habib_system.test_settings
```

این تنظیمات تست‌ها را روی یک دیتابیس SQLite درون‌حافظه‌ای اجرا می‌کند (کوئری‌ها ORM هستند، پس رفتار تست‌ها تغییر نمی‌کند).

اگر ترجیح می‌دهید تست‌ها روی MySQL اجرا شود، یک‌بار با کاربر root این دستور را اجرا کنید و سپس `--settings` را بردارید:

```sql
GRANT ALL PRIVILEGES ON `test_%`.* TO 'habib_user'@'localhost';
FLUSH PRIVILEGES;
```

### ۲) (اختیاری) تغییر اطلاعات اتصال
اگر می‌خواهید کاربر/رمز/نام دیتابیس دیگری استفاده کنید، می‌توانید قبل از اجرا این متغیرهای محیطی را ست کنید تا مقادیر پیش‌فرض بالا را override کنند:

**ویندوز (PowerShell):**
```powershell
$env:DB_NAME="habib_db"
$env:DB_USER="habib_user"
$env:DB_PASSWORD="Habib@12345"
$env:DB_HOST="127.0.0.1"
$env:DB_PORT="3306"
```

**مک/لینوکس:**
```bash
export DB_NAME=habib_db
export DB_USER=habib_user
export DB_PASSWORD="Habib@12345"
export DB_HOST=127.0.0.1
export DB_PORT=3306
```

### ۳) نصب و اجرا
```bash
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

این جریان کامل (ساخت کاربر اختصاصی MySQL، نصب PyMySQL، migrate، ورود با شماره موبایل، ذخیره در جدول `accounts_user`) از صفر روی یک نمونهٔ واقعی MySQL/MariaDB تست و تایید شده است.

### مدیریت مشاغل (حداکثر ۳ شغل برای هر کاربر)
در صفحهٔ پروفایل، بخش «اطلاعات شغلی» حالا واقعی و پویاست:
- هر کاربر می‌تواند حداکثر **۳ شغل** برای خودش ثبت کند (مدل `accounts.Job`، هرکدام با عنوان، سازمان، واحد، نوع استخدام، تاریخ شروع، حوزهٔ فعالیت، مهارت‌ها، و پرچم «شغل فعلی»).
- **موقعیت مکانی شغلی** به‌صورت مجزا برای هر شغل ثبت می‌شود (کشور/استان/شهر/آدرس + مختصات GPS)؛ پیش‌فرض «همان محل سکونت» است (دکمهٔ Current Location — مقادیر از پروفایل کپی می‌شوند) و با برداشتن تیک، کاربر محل کار را جداگانه از فهرست مرجع انتخاب یا با «دریافت GPS برای این شغل» موقعیتش را وارد می‌کند. فیلد «محل کار» از بخش «اطلاعات مکانی» حذف شده است.
- محدودیت ۳ شغل در سطح ویو (`accounts.views.job_add`) بررسی و اعمال می‌شود؛ در صورت رسیدن به سقف، فرم افزودن مخفی و پیام مناسب نشان داده می‌شود.
- هر شغل قابل حذف است (`accounts.views.job_delete`) و فقط توسط مالک همان پروفایل قابل حذف است.
- این جریان (افزودن سه شغل، رد شدن شغل چهارم، حذف و افزودن مجدد) به‌طور کامل تست شده است.

## داده‌های مرجع: اسامی ایرانی (نام‌ها و نام خانوادگی)

فهرست‌های انتخابیِ «نام / نام پدر / نام مادر / نام خانوادگی» در پروفایل از دو جدولِ
مرجع خوانده می‌شوند (`accounts.FirstnameTbl` و `accounts.FamilynameTbl`). این جدول‌ها
با مجموعه‌های عمومیِ اینترنتیِ نام‌های ایرانی پر شده‌اند (منبع و مجوزها در
`accounts/seed_data/ATTRIBUTION.md`):

- `FirstnameTbl` ≈ **۸٬۸۰۰ نام** به‌همراه جنسیت (مردانه/زنانه) و **معادل لاتین**
  (~۸۴٪ نام‌ها) — «نام پدر» فقط نام‌های مردانه/نامشخص و «نام مادر» فقط زنانه/نامشخص
  را نشان می‌دهد.
- `FamilynameTbl` ≈ **۲٬۰۰۰ نام خانوادگی پرتکرار** به‌همراه معادل انگلیسی.

فهرست‌های نام، «فارسی (لاتین)» نمایش داده می‌شوند (مثل «علی (Ali)») تا هم نمایش
دو زبانه باشد و هم جستجو با فارسی یا لاتین ممکن شود.

بارگذاری/تکمیل مجدد (امن و قابل تکرار؛ رکوردهای موجود دست نمی‌خورد):

```bash
python manage.py seed_reference_names
```

مدیریت این جدول‌ها (افزودن/ویرایش/حذف امن + جستجو) از **پنل مدیریت ← «اسامی (نام و
نام خانوادگی)»** در دسترس است. فیلدهای نام در فرم‌های پروفایل، «انتخاب‌گر جستجویی»
دارند: با تایپ، فهرستِ بلند کوتاه می‌شود.

## داده‌های مرجع: اطلاعات مکانی (کشور/استان/شهرستان)

فهرست‌های انتخابیِ «کشور / استان / شهر» در بخش «اطلاعات مکانی» پروفایل (که آدرسِ
**محل سکونت** کاربر است) از سه جدولِ مرجع خوانده می‌شوند (`accounts.CountryTbl`،
`accounts.ProvinceTbl` و `accounts.CityTbl`). `CountryTbl` با **فهرست کامل کشورها**
(مهاجرت داده‌ای ۰۰۲۴) پر شده و به‌عنوان گزینه‌های «تابعیت / ملیت / اقامت دائم» در
اطلاعات شخصی پروفایل هم استفاده می‌شود؛ تقسیمات کشوری (استان/شهرستان) مربوط به
**کشور ایران** است و از تقسیمات کشوری رسمیِ عمومی پر شده (منبع و مجوزها در
`accounts/seed_data/ATTRIBUTION.md`):

- `CountryTbl` = فهرست کامل کشورها (پیش‌فرض: ایران) · `ProvinceTbl` = **۳۱ استان** ·
  `CityTbl` = **۴۸۰ شهرستان**.
- مقادیر انتخابی به‌صورت متنِ فارسیِ همان رکورد در پروفایل ذخیره می‌شوند؛ بنابراین
  هدف‌گیری تیکت‌های انبوه بر اساس شهر/استان/کشور دست‌نخورده می‌ماند.

بارگذاری/تکمیل مجدد (امن و قابل تکرار؛ رکوردهای موجود دست نمی‌خورد):

```bash
python manage.py seed_reference_locations
```

مدیریت این جدول‌ها (افزودن/ویرایش/حذفِ محافظت‌شده + جستجو) از **پنل مدیریت ←
«اطلاعات مکانی (کشور/استان/شهرستان)»** در دسترس است. فیلدهای مکان در فرم پروفایل
و فرم ویرایش ادمین «انتخاب‌گر جستجویی» دارند: با تایپ، جدول مرجع با یک Query واقعی
جستجو و انتخاب می‌شود (فهرست «شهرستان» با استانِ بالادست کوتاه می‌شود).

**نام لاتین (en) استان‌ها و شهرستان‌ها** هم از روی نام فارسی ساخته و در همان جدول‌ها
نگه‌داری می‌شود تا جستجوی «تایپ به انگلیسی» و تطبیقِ نتایجِ GPS/geo ممکن باشد:

```bash
python manage.py enrich_reference_locations_en   # امن و قابل تکرار؛ مقدار دستی را بازنویسی نمی‌کند
```

**هم‌ارزسازی خودکارِ GPS/geo:** هر جا سرویسِ بیرونیِ موقعیت (GPS/نقشه/IP) نامی را
برمی‌گرداند (فارسی یا انگلیسی مانند «Iran»/«Tehran»)، با رکورد مرجع سنجیده و در صورت
یافتنِ هم‌ارزِ مطمئن، **نام رسمی فارسی** همان رکورد ثبت می‌شود (نه نگارش سرویس)؛
مقدارهایی که در فهرست مرجع نیستند دست‌نخورده می‌مانند. منطق در
`accounts/location_ref.py` است و در مسیرهای lookup/update و ذخیرهٔ فرم «اطلاعات
مکانی» پروفایل اعمال می‌شود.

**گسترش فراتر از ایران:** جدول «استان» به‌جای یکتاییِ سراسری، یکتاییِ «کشور+استان» دارد
و پنل مدیریت اجازهٔ افزودن کشور/استان/شهرستانِ جدید را می‌دهد (دادهٔ پروفایلِ موجود
تغییری نمی‌کند، چون مقادیر متن‌اند). برای بارگذاری انبوه یک کشورِ دیگر از CSV:

```bash
python manage.py seed_reference_locations --country-fa قطر --country-en Qatar --file path/to/country.csv
# ستون‌های CSV: country_fa[,country_en],province_fa[,province_en],city_fa[,city_en]
```

## احراز هویت (اپ accounts)

ورود/ثبت‌نام واقعی و مبتنی بر دیتابیس اضافه شده است:

- کاربر فقط با **شمارهٔ موبایل** وارد می‌شود (مدل `accounts.User`، بدون یوزرنیم/ایمیل/رمز عبور).
- **کد تایید (OTP) پیاده‌سازی نشده** — طبق درخواست شما، با ثبت شماره موبایل کاربر بلافاصله وارد می‌شود (اگر شماره جدید باشد، حساب ساخته می‌شود؛ اگر موجود باشد، وارد همان حساب می‌شود).
- به‌محض ساخت کاربر، یک `Profile` خالی به‌صورت خودکار (با سیگنال) برایش ساخته می‌شود.
- مدل `Profile` شامل فیلدهای اصلی است: اطلاعات فردی، شغلی/سازمانی، تحصیلات، مالی، تماس/موقعیت مکانی. بخش‌های متغیرتر (مهارت‌ها، علایق، سوابق، فیلدهای سفارشی و ...) در یک فیلد `extra_data` (JSON) نگه‌داری می‌شوند تا بعداً بدون تغییر مدل قابل گسترش باشند.
- مسیرها: `POST /accounts/login/` (ورود/ثبت‌نام با mobile_number)، `POST /accounts/logout/`.
- صفحات `/dashboard/` و `/profile/` با `@login_required` محافظت شده‌اند و کاربر مهمان به صفحهٔ ورود هدایت می‌شود.
- در بخش کاربری هدر/سایدبار داشبورد و پروفایل، شماره موبایل واقعی کاربر لاگین‌شده و دکمهٔ خروج نمایش داده می‌شود.

### ساخت کاربر ادمین (برای پنل `/admin/`)
```bash
python manage.py createsuperuser
# فقط شماره موبایل و رمز عبور می‌پرسد
```

### نکتهٔ امنیتی مهم
پیاده‌سازی فعلی برای **توسعه/دمو** است: هر کسی با هر شماره موبایلی (حتی متعلق به دیگران) می‌تواند وارد شود، چون کد تاییدی بررسی نمی‌شود. پیش از استفادهٔ واقعی/عمومی، حتماً یک سرویس ارسال و تایید OTP واقعی (مثلاً از طریق پنل پیامک) اضافه کنید.

## دیسک پایدار Archil (نگه‌داری فایل بین اجراها)

برای فایل‌هایی که باید از «یک اجرا» جان سالم به در ببرند (نه فقط از یک درخواست)، ماژول
`cloudstorage/archil_storage.py` با SDK رسمی `archil` به یک دیسک Archil وصل می‌شود:
`get_disk()` (دیسک `ARCHIL_DISK_ID`)، `run_command()` (اجرای فرمان؛ دیسک در `/mnt/data`
مانت است و همان پوشهٔ کاری است)، `write_file()` / `read_file()` / `read_text()`.

این ماژول فقط سمت سرور است؛ کلید API (ابتدای `key-`) فقط از متغیر محیطی
`ARCHIL_API_KEY` خوانده می‌شود و هیچ‌جا چاپ یا در پاسخ برگردانده نمی‌شود.

**تنظیم:** `.env.example` را به `.env` کپی کنید و مقدارها را بگذارید:

```
ARCHIL_API_KEY=key-...        # https://console.archil.com/api-keys (توکن دیسک/مانت adt_… نیست)
ARCHIL_REGION=aws-us-east-1   # کلید و ناحیه باید یکی باشند؛ exec فقط در aws-us-east-1، aws-us-west-2 و aws-eu-west-1
ARCHIL_DISK_ID=               # با اولین اجرای بررسی، خودکار پر می‌شود
```

**بررسی پایداری (نوشتن در یک exec و خواندن در exec دوم):**

```bash
pip install --only-binary=:all: archil==0.17.0
python check_archil_persistence.py
```

اگر `ARCHIL_DISK_ID` خالی باشد یک دیسک تازه ساخته و شناسه‌اش در `.env` ثبت می‌شود؛
توکن یک‌بارمصرفِ مانت هیچ‌جا چاپ نمی‌شود. کد خروج غیرصفر یعنی بازخوانی با نوشته هم‌خوان نبوده است.
